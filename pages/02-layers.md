# 02. 4개 레이어, 도서 대출 시스템에 대입하면?

## 4개 레이어의 기본 개념

클린 아키텍처는 코드를 4개의 층(레이어)으로 나눕니다. 안쪽으로 갈수록 "변하지 않는 핵심 규칙", 바깥쪽으로 갈수록 "언제든 바뀔 수 있는 세부 기술"입니다. 도서 대출 시스템에 비유하면 이렇게 이해할 수 있습니다.

- **Entities (엔티티) — 가장 안쪽, 핵심 업무 규칙**
  시스템에서 가장 중요한 개념과 규칙 그 자체입니다. "책 한 권은 동시에 한 명에게만 대출된다", "회원은 최대 5권까지 빌릴 수 있다" 같은, 앱이든 웹이든 어떤 형태로 만들어도 변하지 않는 규칙입니다. `Book`, `Member`, `Loan`이 여기에 해당합니다.

- **Use Cases (유스케이스) — 애플리케이션 동작 규칙**
  사용자가 시스템으로 실제로 "하는 일"을 정의합니다. "책을 빌린다", "책을 반납한다", "대출을 연장한다" 같은 시나리오입니다. 엔티티(규칙)를 가져와 순서대로 실행하는 흐름을 담당합니다. 단, 화면에 어떻게 보여줄지·어떤 DB를 쓸지는 몰라도 됩니다.

- **Interface Adapters (인터페이스 어댑터) — 변환기**
  안쪽(엔티티·유스케이스)과 바깥쪽(DB·웹) 사이에서 데이터 형태를 서로 맞게 번역해 주는 층입니다. 예를 들어 DB 테이블의 한 줄을 `Book` 객체로 바꾸거나, 유스케이스 결과를 화면에 보낼 JSON 형태로 바꿉니다. "통역사" 역할이라고 보면 쉽습니다.

- **Frameworks & Drivers (프레임워크와 드라이버) — 가장 바깥쪽, 세부 기술**
  실제로 쓰는 도구와 기술입니다. 웹 프레임워크(FastAPI), 데이터베이스(SQLAlchemy, PostgreSQL) 같은 것들입니다. 가장 자주 바뀌고 교체되는 부분이라, 일부러 가장 바깥에 두어 안쪽 규칙이 영향받지 않게 합니다.

> 핵심 한 줄: **안쪽일수록 "무엇을(업무 규칙)", 바깥쪽일수록 "어떻게(기술)"** 를 담당합니다.

## 프로젝트 파일에 대입하기

이번 프로젝트에서 각 레이어가 실제로 어떤 클래스·파일에 해당하는지에 관한 예입니다. 

| 레이어 | 파일 |
|---|---|
| **Entities** | `domain/entities.py` — Book, Member, Loan |
| **Use Cases** | `application/use_cases.py` — BorrowBook, ReturnBook, ExtendLoan |
| **Interface Adapters** | `adapters/` — SqlBookRepository, LoanResponse 스키마 |
| **Frameworks & Drivers** | `main.py`, `infrastructure/db.py` — FastAPI, SQLAlchemy |

## 의존성 흐름

안쪽 레이어는 바깥쪽 레이어를 절대 import하지 않습니다. import 방향이 곧 의존성 규칙입니다.

```
domain          →  (없음)
application     →  domain
adapters        →  domain, application
infrastructure  →  (외부 라이브러리만)
main.py         →  전 레이어  ← 유일한 연결 지점
```

이 규칙 덕분에 `domain/`과 `application/`은 FastAPI, SQLAlchemy를 전혀 모르는 상태로 유지됩니다. 프레임워크를 교체해도 안쪽 두 레이어는 수정할 필요가 없습니다.

이 4개 layer  에 대한 이름은 책마다 조금씩 다르게 표현되기도 합니다. 여기에서는 위의 표현대로 엔티티, 유스케이스, 인터페이스 어댑터, 프레임워크와 드라이버로 구분하도록 하겠습니다.
